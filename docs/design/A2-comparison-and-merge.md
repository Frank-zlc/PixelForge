# A2 · 两份方案的对比与合并

> 研究记录：本文件写作时 PF-DES-001 的数据模型、接口和交付文档尚未完成；现在三份文档已经补齐并按用户指示进入 N1 开发。本文保留当时的比较过程；实际开发方案以 [PF-DES-001](001-2026-09-22-visual-image-notebook/README.md) 为准。文中关于 `crop` 失效和正确 BGR/RGB 转换会改变同一物理颜色 HSV 含义的判断，经代码核查均不成立，详见主方案的核查更正。

> 本文采用 [PF-DES-001 的文档规范](README.md) 的 YAML 元数据格式——这是对比的第一个结论：那套规范比我在 A1 §0 里写的更好，直接采用。

对比对象：
- **001** = [PF-DES-001 图形化图片实验本](001-2026-09-22-visual-image-notebook/README.md)（README + UI + MHXY_REUSE，共 367 行）
- **A1** = [图像能力库与实验台](A1-image-capability-library.md)（433 行）

---

## 1. 结论

**没有一份该被丢掉，而且它们的强弱几乎是互补的。**

001 强在**调查、方法和治理**：它查了 MHXY 的分支关系，抓出了旧代码里的真实缺陷（包括我方案里一处判断失误），把验收方法定义到了"用什么样图、留什么证据、没改善就不发布"的程度，文档规范本身也成体系。

A1 强在**机制和落地件**：注册表怎么写、参数 schema 长什么样、返回类型是什么、建哪几张表、开哪些接口——这些是可以直接照着敲代码的东西。

**决定性的事实是：001 的 README 引用了 `DATA_MODEL.md`、`API_EXECUTION.md`、`DELIVERY.md` 三份子文档，而这三份都不存在。** 那正是数据模型、接口执行、任务验收——正好是 A1 唯一有、001 唯一缺的三块。

所以建议不是二选一，而是：

> **以 001 为主线方案，把 A1 的机制部分改写成它缺的那三份子文档，A1 本体标 `superseded` 并保留原文。**

## 3. 001 赢我的地方（含我必须更正的判断）

### 3.1 它抓到了我看漏的真实缺陷

MHXY_REUSE §4 列了 8 条，其中这几条我完全没看到：

- `get_words_xy` 的 `words_color` 参数在调用处被写死成 `'Y'`——参数形同虚设
- `findContours` 三返回值解包、`numpy.int`——在现代 numpy/OpenCV 上直接报错，不是"顺手改改"能过的
- `test` 分支 `ImageHandle.template_match` 的 `img_cv[ay1:ay2, ax1, ax2]`——逗号写成冒号，这是个真 bug
- `static_capture.get_task_info` 里的红通道减蓝通道——一个可抽象成通用算子的技巧，我整个漏掉了

### 3.2 它推翻了我对 `template_similarity_check` 的评价 ⚠

**这条我错了，必须更正。** A1 §2.2 我写"这是这批代码里最有价值的一个"。001 指出了它的指标缺陷：

> 使用交集像素之和除以模板像素之和；未处理模板无前景，指标不惩罚额外噪声

这是对的，而且比"缺陷"更严重——`sum(交集)/sum(模板)` 本质上是**覆盖率/召回**，它只问"模板的前景有没有被盖住"，完全不问"区域里有没有多余的东西"。后果是：**一块纯黄色的区域，对一个黄字模板会得到接近 1.0 的满分。** 这正是二次校验最该拦住的误报类型。另外模板全黑时分母为 0，直接除零。

更正后的判断：这个函数是**最有价值的候选思路**（用独立证据复核匹配结果，方向完全正确），但**指标必须先修**——至少要同时给出覆盖率和精确率，或者直接用 IoU。而且按 001 的要求，得在正负样例集上先证明它真的减少误报，再决定发不发布。

### 3.3 它的验收方法比我的强一个量级

我的 D6 是 golden fixture + sha256：**只能测"输出没变"，测不了"输出对不对"**。回归和验证是两件事，我把前者当成了后者。001 §5 要的是人工标注的正负样例集、红色色相回绕覆盖、靠边目标、非零 ROI——那才是能回答"这个算法好不好用"的东西。

### 3.4 它的交互模型比我的线性链更好

我把实验本设计成线性算子链。001 是**具名输出 + 输入下拉引用**（"步骤 2 / mask"），并且明确拒绝把 OCR 文本当图片自动传给下一步。这是个更强的模型，线性链只是它的特例。模板匹配需要"待查图 + 模板图"两个输入——线性链根本表达不了。**A1 的 D5 应当整体让位于这个模型。**

### 3.5 它对工期的态度比我对

我给了"2–3 天""3–4 天"。001 写的是"工期在范围确认和 N1 技术验证后评估，本文不以未验证数字承诺性能或交付日期"。**它是对的**，我那些数字是猜的，猜错了会变成压力。

## 4. A1 赢它的地方

### 4.1 目录的真相来源（001 完全没解决）

001 说"可用性按实际能力判断：实现已注册、适配器已接入、依赖可用才显示可运行"——**目标对，但没给机制**，而现有实现是手写元组 upsert 进 SQLite，`function_name` 是没人校验的字符串。今天 `crop` 声明实现是 `_crop`，而 `_crop` 的函数体是 `return image.copy()`，什么也没裁，没有任何报错。

A1 的 D1（装饰器注册，`qualname` 自动填、`availability` 从依赖探测派生）是这条目标的落地手段。没有它，"按实际能力判断"只是一句愿望。

### 4.2 `OpResult` 的具体类型（001 只有方向）

两份都发现了同一件事——`device_only` 是入口状态而非算法约束（001 说得很清楚）。但 001 停在"统一工具契约、返回具名输出"，没有定义那个类型。A1 的 D2 给了六个字段，其中 `artifacts` 有个 001 没提的用法：**接住 MHXY 那些 `cv2.imwrite` 调试图**。你当初写那些 imwrite 是因为没地方看中间结果——实验台就是那个地方，调试副作用变成正式返回值。

### 4.3 参数 schema 与 `when`（001 只说"生成表单"）

A1 的 `Choice/Slider/IntRange` + `when` 条件显示是"加算子时前端零改动"的具体实现。001 的详情页设计里列了"中文说明、默认值、范围、枚举、单位；由工具参数定义生成表单"——描述的正是这个东西，但没说它长什么样。

### 4.4 纯函数约束的强制手段

001 写了约束（"不读取页面状态、不获取设备、不自行覆盖原图"），A1 给了执法方式：参数化测试遍历注册表，断言入参未被修改、两次调用逐像素相同、工作目录下没有新文件。第三条专治 imwrite 复发——鉴于 MHXY 里有 6 处 imwrite，这条不是假想威胁。

### 4.5 三份缺失子文档的内容

DDL 5 张表、10 个接口、分期任务。其中 `image_run` 表是两份都该有而只有 A1 有的：它让"我有多少功能"升级成"**哪些功能我真在用、多快、失败率多少、哪些从来没人点过**"。半年后砍功能时这是唯一依据。

### 4.6 与既有架构的挂钩

A1 把 Operator 定位为 ARCHITECTURE §3 的**第五个插件扩展点**（原有 DeviceProvider / Locator / Exporter / Listener）。这不只是命名——它意味着第三方用同一套装饰器加算子而不动核心，与项目已确立的插件哲学一致。001 没有把新能力接到这条线上。

## 5. 两份都没做好的

1. **色彩空间没锁死。** A1 说"HSV 阈值数值逐字保留"，001 说"输入统一规范与颜色空间声明"——两条放在一起才完整，单独任一条都会出事：MHXY 走 `COLOR_BGR2HSV`，现有 `tool_catalog` 走 `COLOR_RGB2HSV`，**同样的 H 值在两者下含义不同**（红蓝互换会让色相偏移）。移植时必须同时固定数值和色彩空间，并用一张已知色块图做断言。
2. **谁来保证目录数字不注水，没有机制。** 001 定了规矩（"只有实现注册、校验、依赖检查、演示和验收齐备才进入可用数量统计"），但规矩要靠人执行。应该让 `availability` 完全派生（A1 D1），再加一条测试：声明 `ready` 的算子必须有可运行的 demo 与非空验收记录，否则构建失败。
3. **两份都没说清实验本与设备项目的关系。** 001 说"可独立存在，也可关联设备项目"，A1 说"导出成 Step"。但"同一段处理链，在实验台是 cell，在脚本里是 Step"这件事的数据映射，两边都没定义。这应该是 DELIVERY 里 N4 的前置设计，不能拖到写代码时临时决定。

## 7. 具体行动

1. **A1 §4 数据模型 → 001 的 `DATA_MODEL.md`**。补两处：素材的 EXIF 归一化与色彩空间字段；`image_pipeline_cell` 改为支持引用任意前序步骤的具名输出（`input_ref` 替代隐式顺序）。
2. **A1 §5 接口 → 001 的 `API_EXECUTION.md`**。补 001 已定义而 A1 没有的执行语义：运行到此/从此重跑/运行全部、revision N、取消与超时、服务重启后的"已中断"。
3. **A1 §8 分期 → 001 的 `DELIVERY.md`**。**去掉所有天数**，改用 001 的 N0–N5 加每阶段退出条件与证据要求。
4. **把 A1 的 D1/D2/D3/D4 写进 001 README §4「建议架构与关键决定」**，作为第 2 条"统一工具契约"的具体化。
5. **更正 A1 §2.2 对 `template_similarity_check` 的评价**，并在 MHXY_REUSE 的移植清单里把它的优先级条件化：先修指标、先过样图集。
6. **补查 MHXY `test` 分支**的 8 个独有提交（A1 完全没看这个分支），确认 `utilities/image_handle.py` 里还有没有值得移植的东西。
7. **A1 本体标 `superseded`**，在开头指向 001 与本文，保留原文不删——按两份规范共同的要求，被推翻的判断连同推翻理由要留着。
