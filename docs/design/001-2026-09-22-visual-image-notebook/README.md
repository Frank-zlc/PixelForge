# PF-DES-001：图形化图片实验本

**状态：开发中。用户于 2026-09-22 指示对比 A1/A2、更新方案并按阶段开始开发；N1 已完成，N2—N5 待开发。实际证据见 [阶段记录](DELIVERY.md)。**

## 1. 目标与阅读顺序

将 PixelForge 扩展为通用图片处理 IDE：从本地图片、目录或设备截图开始，用图形化步骤选择工具、调整参数、框选区域、查看中间结果，并保存整个实验以便重跑与对比。体验借鉴 Jupyter：每个步骤都有输入、配置和输出，用户能看见处理过程。

推荐先看本文的范围与开发顺序，再看 [页面设计](UI.md)；技术细节分为 [数据模型](DATA_MODEL.md)、[接口与执行](API_EXECUTION.md)、[开发与验收](DELIVERY.md)。[MHXY 复用评估](MHXY_REUSE.md) 保存分支结论、来源和算法移植建议。

### A1/A2 对比后的取舍

比较依据：[A1 备选方案](../A1-image-capability-library.md)、[A2 对比](../A2-comparison-and-merge.md) 及当前工作区代码。A2 写作时认为三份技术子文档不存在；现在 [数据模型](DATA_MODEL.md)、[接口执行](API_EXECUTION.md)、[交付验收](DELIVERY.md) 已补齐，其结论按下表更新。

| 议题 | 本方案采用的做法 | 原因 |
| --- | --- | --- |
| 功能目录真相 | 已发布算子的定义由代码注册表提供；数据库保存版本快照、示例、用户文案与运行记录；可运行状态由注册、适配器、依赖和验收门槛共同派生 | 避免手写状态与实现漂移，同时保留历史可追溯性 |
| 结果结构 | 采用具名且带类型的端口，结果包含 image、mask、regions、points、metrics、text、artifacts、notes；中间调试图作为正式产物返回 | 支持 OCR、模板匹配、多输入与可检查中间结果 |
| 参数与验证 | 同一声明式 schema 驱动后端校验和前端表单，支持 `when` 条件；纯图像算子测试覆盖输入不可变、确定性、无隐式写盘 | 新增功能时减少前后端手工同步 |
| 效果图 | 由锁定版本与样图生成，保存哈希做回归；正确性另用人工标注的正负样图验收 | 输出未变化不等于算法正确 |
| 实验结构 | 顺序单元，但输入可引用任意前序步骤的具名输出或素材；先不采用 A1 的隐式单链 | 双图匹配、mask 与文字输出都需要显式类型和来源 |
| 数据表 | 采用九张逻辑表（含迁移、版本、示例、素材、实验与运行）；统计从 `step_runs` 聚合，暂不另建 A1 的单步 `image_run` | 能保留不可变运行快照，避免重复权威数据 |
| 扩展机制 | Operator 作为候选第五扩展点；N1 仅注册可信内置算子，第三方加载策略在 N4 设计 | 与既有扩展理念一致，避免现在就允许任意路径导入代码 |
| 设备脚本映射 | N4 先定义实验步骤到脚本 Step 的显式映射与不支持项，再开发导出 | 不把离线工具链悄悄等同设备动作 |

核查更正：`crop` 在 `process_image()` 中先应用 ROI，`_crop()` 复制的是裁好的视图，现有裁剪 API 测试通过；可改名/封装以降低误解。OpenCV 的 `BGR2HSV` 和 `RGB2HSV` 对**各自正确表示的同一物理颜色**产生相同 HSV，问题在通道表示与转换码不匹配。MHXY 参数迁移必须同时记录输入通道、转换码和数值，并用已知色块验证。模板覆盖率不惩罚额外前景且空模板可除零，因此二次校验需先引入精确率/IoU 与空前景处理，再以正负样图证明改善。

### 核心流程

~~~text
导入目录 → 选择图片 → 新建实验本
  → 裁剪区域 → 提取颜色 → 二值化 → OCR
  → 对比每一步的输入/输出 → 调整参数 → 重跑受影响步骤
  → 保存实验、结果和运行历史 → 后续批量应用于其他图片
~~~

功能目录同时承担“有什么”和“怎么用”：能按类别查找、看处理前后效果、查看工具函数与介绍，并一键加入实验本。

## 2. 当前基线与整改原因

检查日期为 2026-09-22。PixelForge HEAD 为 `77bb3ea`，工作区另有未提交改动；本方案按实际工作区分析，不能仅凭该提交还原全部原型。实现阶段开始前需记录经确认的代码基线，保留已有改动。

| 项目 | 当前实现 | 需要整改 |
| --- | --- | --- |
| 前端 | 原生 HTML/CSS/ES modules，静态服务 | 复用现有方式，拆分页面和公共组件 |
| 功能目录 | SQLite 单表，12 条目录记录 | 工具版本、参数说明、真实可用状态、多个效果示例 |
| 单步离线处理 | 已有 6 个可执行工具，可选本地文件或目录、ROI、下载结果 | 接入统一输入输出与持久化 |
| 处理链 | 当前一次处理一张输入图 | 可编辑步骤、前序输出引用、局部重跑 |
| 素材 | 浏览器 File 对象和临时结果 URL | 显式导入托管存储，刷新及重启后可恢复 |
| 结果 | HTTP 返回 PNG | 图片、掩码、文本、框选标注、分数、表格等多种结果 |
| 离线识别 | 模板匹配、OCR、差异算法已能接收数组 | 补齐工具适配器、第二输入和结果展示 |
| 项目保存 | 设备项目为 JSON + PNG 文件 | 实验本另用 SQLite，不同时维护两份权威数据 |
| 文档 | 原架构仍有 React、ProjectStore SQLite、ProcessPool 等设想 | 随实现同步现状；本方案不代表这些设想已经落地 |

关键代码依据：[工具目录及原型实现](../../../backend/src/pixelforge/vision/tool_catalog.py)、[图片 API](../../../backend/src/pixelforge/api/image_tools.py)、[图片页](../../../frontend/tools.js)、[项目存储](../../../backend/src/pixelforge/store/projects.py)、[匹配算法](../../../backend/src/pixelforge/vision/matching.py)、[OCR](../../../backend/src/pixelforge/vision/ocr.py)。

现有历史测试数字不作为本方案新能力的验收证据。

### 当前目录统计的准确含义

- 6 项可在图片页执行：区域裁剪、灰度图、颜色提取、边缘检测、二值化、彩色文字增强。
- 3 项算法已有、图片页待接入：模板匹配、OCR、画面差异。当前 `device_only` 只是入口状态，不代表算法必须连接设备。
- 3 项规划记录：文字区域定位、模板二次校验、目录批量处理。其中批量处理属于工作流能力，后续应单独统计。
- 现有 `color_mask` 对外返回的是保留选中色彩的 RGB 图；新契约需额外输出真正的单通道掩码。

**N1—N3 构成首个完整版本**，交付“导入 → 多步处理 → 识别/匹配 → 保存 → 重开重跑”的完整流程。N4—N5 保留为后续范围，在前一阶段验收后细化。N1 单独交付的是基础层，不能称为完整图形化实验本。

首版支持单机、单用户、顺序步骤，以及引用任意前序步骤的具名输出。首版范围暂不包含任意 Python 代码单元、Jupyter 内核、.ipynb 兼容、多人协作、分布式调度、自由连线与循环节点。将来确有需求时另起方案。

## 4. 建议架构与关键决定

~~~mermaid
flowchart TD
    Files[本地图片与目录] --> Assets[素材库与标准化解码]
    Device[设备无损截图] --> Assets
    Catalog[工具目录与版本] --> Notebook[实验本与步骤编辑]
    Assets --> Notebook
    Notebook --> Snapshot[不可变运行快照]
    Snapshot --> Runner[执行调度与工具适配器]
    Runner --> Vision[现有视觉算法与重构算法]
    Vision --> Results[具名输出与运行记录]
    Results --> Preview[对比预览和后续步骤输入]
    Results --> Storage[SQLite 元数据与产物文件]
~~~

1. **页面分层**：实验本、功能目录、素材库、设备工作台；二级页面负责工具详情和运行详情。目录页保留快速体验，复杂处理进入实验本。
2. **统一工具契约**：算法接收明确类型的输入与参数，返回具名输出；工具函数不读取页面状态、不获取设备、不自行覆盖原图。
3. **可用性按实际能力判断**：实现已注册、适配器已接入、依赖可用才显示可运行。Tesseract/语言包缺失时说明原因，其余工具继续可用。
4. **存储职责明确**：沿用 `image_tools.sqlite3` 并显式迁移，保存工具和实验数据；图片及大结果放运行数据目录；原设备 ProjectStore 保留 JSON。实验本可独立存在，也可关联设备项目。
5. **结果可追溯**：运行锁定素材、工具版本、参数、ROI 和步骤快照；变更草稿不改写历史结果。
6. **分步改造**：保留现有 ES modules 和设备入口，按新增模块拆分；暂不把更换前端框架作为前置条件。
7. **执行可控制**：后端维持现有单服务进程约束，图片计算由受控子进程执行。首版默认一次执行一个计算步骤，具有队列、取消、超时和异常恢复。

## 5. 开发顺序

| 阶段 | 核心产物 | 用户可验证的结果 |
| --- | --- | --- |
| N0 评审 | 本方案与范围确认 | 页面、数据和顺序符合预期 |
| N1 基础整改 | 素材库、版本化工具目录、契约、6 项工具适配 | 离线导入能保存，工具介绍和效果对应实际版本 |
| N2 实验本 | 步骤编辑、运行、保存、历史、失效传播 | 裁剪到二值化能串联，刷新及重启后可重跑 |
| N3 识别与比较 | OCR、模板匹配、差异适配器 | 图片、文字、标注、分数能同时查看 |
| N4 复用与批量 | 流程模板、批量任务、导出、设备快照 | 一个实验应用于目录多张图片 |
| N5 算法深化 | MHXY 高价值算法重构与样例库 | 在明确样图集上看到效果和适用边界 |

每个阶段包含设计更新、实现、针对性验证和使用说明；具体任务与退出条件见 [DELIVERY.md](DELIVERY.md)。工期在范围确认和 N1 技术验证后评估，本文不以未验证数字承诺性能或交付日期。
