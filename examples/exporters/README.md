# 导出插件示例

PixelForge 核心只带两个与业务无关的导出器：原生 JSON 和 pytest。
面向某个具体执行引擎的导出器属于**那个项目**，不属于这里——它编码的是那个引擎的
action 枚举、字段名和限制。一旦核心收了第一个，第二个引擎就会要求同等待遇，
注册表最后变成一张别人格式的清单。

所以这类导出器做成插件。

## 用法

```bash
export PIXELFORGE_EXPORTER_PLUGINS=/path/to/my-plugins
uvicorn pixelforge.main:app --port 8420
```

目录里每个 `*.py`（下划线开头的除外）会被导入，并注册它导出的
`EXPORTER` 实例或 `get_exporter()` 工厂。插件导入失败只记日志不中断启动——
一个可选导出器写错了，不该让整个工具起不来。

插件是被执行的 Python 代码。这与本工具其余部分的信任级别一致（它本来就在跑
驱动手机的脚本），但意味着插件目录和源码一样敏感，也是发现机制做成显式配置
而不是扫描文件系统的原因。

## `constrained_profile.py`

一个完整可用的例子：把 PixelForge 的 Step 模型降级到一个**受限的步骤 profile**
格式——六个动作、仅归一化坐标定位、仅 OCR 文本等待、步骤名唯一、上限 30 步。

这个形状在实际项目里很常见，原因也正当：下发到边缘节点执行的 profile 不该能
携带任意行为，所以用 `extra="forbid"` 和固定枚举把它锁死。代价是表达力，而
**降级必须报警**——静默丢掉一个断言，会产出在 IDE 里通过、在生产里少做事的
脚本，这是最糟的失败形态。

复制这个文件，把 `_ACTION_MAP`、`_MAX_STEPS`、`_WORKFLOW_NAMES` 改成你自己引擎
的约定即可。
